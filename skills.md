# MedScribe360 - Project Knowledge Base

Generated from the local repository on 2026-06-08. The user-facing request names the project **MedScribe360**, while the README, package metadata, HTML title, and UI copy mostly use **VoiceScribe**, **VoiceScribe-360**, or **MedScribe 360**. This document treats those names as the same codebase and calls out the naming inconsistency as technical debt.

## 1. Project Overview

### Purpose of the Project

MedScribe360 is a full-stack healthcare MVP that aims to reduce clinical documentation effort by combining patient symptom logging, doctor-facing consultation records, and AI-assisted medical information extraction.

The implemented system currently supports:

- Public product landing page for the VoiceScribe/MedScribe concept.
- Doctor and patient registration/login.
- JWT-protected doctor and patient routes.
- Patient symptom text logging.
- AI extraction of structured symptom details from free-text patient input.
- Doctor dashboard for viewing appointments and medical records.
- Mock doctor voice-consultation flow that saves a synthetic SOAP-style medical record.
- MongoDB persistence for users, appointments, medical records, login sessions, and symptom logs.

### Problem It Solves

Healthcare consultations often lose time to documentation, and patients often forget symptom details before seeing a doctor. This project addresses those problems by:

- Letting patients capture symptom descriptions before consultation.
- Converting symptom text into structured fields such as symptoms, duration, severity, frequency, progression, and notes.
- Giving doctors a dashboard for consultation-related records.
- Demonstrating how AI could support SOAP-note generation, although the current doctor-side SOAP flow is mocked rather than generated by a model.

### Target Users

| User Type | Needs Addressed | Implemented Experience |
|---|---|---|
| Patients | Log symptoms before visits, maintain a symptom history, prepare better for consultation | Patient dashboard and symptom logging route at `frontend/src/components/PatientDashboard.jsx` and `frontend/src/components/SymptomLogging.jsx` |
| Doctors | Review appointments, create consultation records, reduce manual documentation | Doctor dashboard and mock consultation flow at `frontend/src/components/DoctorDashboard.jsx` |
| Admin/Operations | Seed demo data and run the app locally | Backend seed script at `backend/seed.js` |
| Developers | Learn full-stack React, Express, MongoDB, JWT, and Gemini integration patterns | Separate `frontend` and `backend` applications with clear package manifests |

### Main Workflow

1. A visitor lands on `/` and reads product messaging in `LandingPage`.
2. The visitor creates an account or signs in as either doctor or patient.
3. The frontend stores the returned JWT token and user object in `localStorage`.
4. `ProtectedRoute` checks the stored user role and gates doctor/patient routes.
5. A patient opens the dashboard and starts symptom logging.
6. Typed symptom text is sent to the Express API.
7. The Express API calls the local Python Flask LLM service.
8. The Flask service sends the symptom prompt to Gemini `gemini-2.5-flash`.
9. Structured symptom JSON is stored in MongoDB.
10. A doctor opens the dashboard, fetches appointments and medical records, and can run a mocked voice-consultation flow that saves a medical record.

### Business Objective

The project is positioned as a hackathon-grade healthcare documentation product. Its business objective is to demonstrate a future clinical assistant that:

- Reduces doctor documentation time.
- Improves patient recall before consultation.
- Creates structured health records from natural language.
- Establishes a foundation for future clinical intelligence, appointment management, and health trend analysis.

The current implementation is an MVP/prototype, not a production-ready clinical platform.

### Backend Architecture

#### Framework Used

The backend is a Node.js Express application:

- Express `^4.22.1`
- MongoDB ODM: Mongoose `^8.0.0`
- Authentication: JSON Web Tokens using `jsonwebtoken`
- Password hashing: `bcryptjs`
- CORS: `cors`
- Environment loading: `dotenv`
- HTTP client for LLM service: `axios`
- Development runner: `nodemon`

The backend package is defined in `backend/package.json`.

#### Server Architecture

`backend/index.js` is the server entrypoint. It:

- Loads environment variables with `dotenv`.
- Creates an Express app.
- Enables CORS globally using `app.use(cors())`.
- Enables JSON and URL-encoded body parsing.
- Connects to MongoDB using `MONGODB_URI` or local fallback `mongodb://localhost:27017/voicescribe`.
- Mounts auth routes at `/api/auth`.
- Mounts application routes at `/api`.
- Exposes `GET /health`.
- Starts listening on `PORT` or `3000`.

There is no separate app/server split, dependency injection container, service layer, or controller directory. Route handlers are implemented inline.

#### Route Organization

| File | Mounted Path | Responsibility |
|---|---|---|
| `backend/index.js` | `/health` | Backend health endpoint |
| `backend/auth.js` | `/api/auth` | Registration, patient-specific registration, login |
| `backend/routes.js` | `/api` | Appointments, medical records, doctors, symptoms |
| `backend/middleware.js` | Used per protected route | JWT verification middleware |

#### Controllers

There are no dedicated controller files. Controller logic lives directly inside Express route callbacks:

- `backend/auth.js` handles user creation, password hashing, JWT issuing, login-session recording.
- `backend/routes.js` handles appointment queries, medical record queries, doctor lookup, symptom persistence, and LLM calls.

#### Services

There is no Node.js service layer. The closest service boundary is the Python LLM microservice:

- `backend/llm-service/main.py` exposes a Flask API at `POST /extract`.
- `backend/llm-service/llm.py` wraps Google Gemini generation and JSON parsing.

#### Middleware

`backend/middleware.js` exports a single `auth` middleware:

- Reads the `Authorization` header.
- Removes the `Bearer ` prefix.
- Verifies the JWT.
- Adds decoded user data to `req.user`.
- Returns `401` if the token is missing or invalid.

Protected backend routes use this middleware in `backend/routes.js`.

#### Authentication Flow

Registration flow:

1. `POST /api/auth/register` receives account fields.
2. Backend checks `User.findOne({ email })`.
3. Password is hashed with `bcrypt.hash(password, 12)`.
4. User data is built based on `userType`.
5. User is saved to MongoDB.
6. JWT is signed with `{ userId, userType }` and `expiresIn: '7d'`.
7. Response returns `token` and a safe user object without password.
8. Frontend stores token and user in `localStorage`.

Login flow:

1. `POST /api/auth/login` receives `email`, `password`, and `userType`.
2. Backend finds the user by email and role.
3. Password is verified with `bcrypt.compare`.
4. JWT is signed with `{ userId, userType }`.
5. A `LoginSession` document records `userId`, IP address, and user agent.
6. Response returns `token` and safe user object.
7. Frontend navigates to the role-specific dashboard.

Important security issue: `auth.js` and `middleware.js` define a fallback `JWT_SECRET`, but `login` and the middleware verification call use `process.env.JWT_SECRET` directly in some places. If `JWT_SECRET` is missing, login and protected route verification can fail even though fallback constants exist.

### Database Architecture

#### Database Technology

The project uses MongoDB through Mongoose. The default local database URI is:

```text
mongodb://localhost:27017/voicescribe
```

All schemas are defined in `backend/models.js`.

#### Schema Design

The schema design centers on `User` documents and references them from appointment, medical record, login session, and symptom log documents.

Main relationships:

- `Appointment.doctorId` references `User`.
- `Appointment.patientId` references `User`.
- `MedicalRecord.doctorId` references `User`.
- `MedicalRecord.patientId` references `User`.
- `MedicalRecord.appointmentId` references `Appointment`.
- `LoginSession.userId` references `User`.
- `SymptomLog.userId` references `User`.
- `SymptomLogDoctor.userId` references `User`.

#### Collections/Tables

MongoDB collections are created from these Mongoose models:

- `User`
- `Appointment`
- `MedicalRecord`
- `LoginSession`
- `SymptomLog`
- `SymptomLogDoctor`

`SymptomLogDoctor` is the collection actually used by `/api/symptoms`. `SymptomLog` is defined but not used by current routes.

#### Indexes

Explicit indexes:

- `User.email` has `unique: true`, creating a unique email index.

Implicit indexes:

- MongoDB creates `_id` indexes for every collection.

Missing indexes that would matter later:

- `Appointment.doctorId`
- `Appointment.patientId`
- `Appointment.date`
- `MedicalRecord.doctorId`
- `MedicalRecord.patientId`
- `MedicalRecord.createdAt`
- `LoginSession.userId`
- `SymptomLogDoctor.userId`
- `SymptomLogDoctor.createdAt`

## 7. AI Features

### AI Feature: Structured Symptom Extraction

**Input**

Free-text symptom description from the patient, submitted through `SymptomLogging.jsx`.

Example shape:

```json
{
  "symptoms": "I have had a mild headache for three days and nausea in the morning"
}
```

**Processing**

1. React sends `symptomsText` to `POST /api/symptoms`.
2. Express route sends `{ symptoms: symptomsText }` to `http://localhost:5000/extract`.
3. Flask receives the text and calls `run_llm(symptom_text)`.
4. `run_llm()` builds a prompt with strict extraction rules.
5. Gemini generates JSON.
6. Python strips Markdown code fences if present.
7. Python parses the result with `json.loads`.
8. Express stores the parsed object as `structuredData`.

**Model Used**

`gemini-2.5-flash` through the `google-genai` Python package.

**Output**

The expected output shape is:

```json
{
  "symptoms": [],
  "duration": "",
  "severity": "",
  "frequency": "",
  "progression": "",
  "notes": ""
}
```

**Limitations**

- The AI service requires `GEMINI_API_KEY`.
- There is no schema validator after the model response.
- There is no timeout, retry policy, circuit breaker, or queue.
- If Gemini returns invalid JSON, the Flask service returns a parsing error.
- If the Flask service fails, Express still saves the symptom with `structuredData: null`.
- The prompt explicitly says not to diagnose, so it is an extraction feature, not a diagnostic feature.
- Health data is sent to an external AI provider without visible consent, de-identification, retention controls, or audit tracking.

### AI Feature: Doctor SOAP Notes

**Input**

The UI implies voice consultation input, but the implemented input is simulated transcription text in `DoctorDashboard.jsx`.

**Processing**

No AI processing exists for doctor SOAP notes. `stopRecording()` creates hardcoded SOAP notes, diagnosis, and prescription values in a `mockRecord`.

**Model Used**

None in the current doctor-side implementation.

**Output**

Hardcoded medical record fields:

- Subjective
- Objective
- Assessment
- Plan
- Diagnosis
- Prescription

**Limitations**

- No real audio capture.
- No speech-to-text.
- No LLM SOAP-note generation.
- No doctor review/edit/approve workflow beyond saving the mock record.
- No safety checking for generated medical content because content is not generated.

Status: ⚠ Partially Completed as a mock/prototype.

## 8. Security Implementation

### Authentication

Implemented:

- Email/password authentication.
- `bcryptjs` password hashing with salt rounds set to `12`.
- JWT tokens signed with `{ userId, userType }`.
- 7-day token expiry.
- Frontend token attached as `Authorization: Bearer <token>`.
- Login session persistence with IP address and user agent.

Files:

- `backend/auth.js`
- `backend/middleware.js`
- `frontend/src/services/api.js`
- `frontend/src/contexts/AuthContext.jsx`

### Authorization

Implemented:

- Frontend route-level role checks through `ProtectedRoute`.
- Backend list queries filter appointments and medical records based on `req.user.userType`.
- Backend protected routes require a valid JWT.

Missing or weak:

- Backend does not consistently enforce that only doctors can create medical records.
- Appointment creation allows authenticated users to submit arbitrary doctor and patient IDs.
- Medical record creation does not validate that the patient exists or that an appointment belongs to the doctor.
- Frontend route protection depends on local stored user data and does not verify the token on page load.

### Password Handling

Implemented:

- Passwords are hashed before storage using bcrypt.
- API responses do not return password hashes.

Missing or weak:

- No password reset flow.
- No password complexity beyond frontend minimum length.
- No backend password length/complexity validation visible.
- No rate limiting against brute-force login attempts.

### Token Management

Implemented:

- JWT stored in browser `localStorage`.
- Token sent as Bearer token for protected API calls.
- Logout clears token and user from `localStorage`.

Risks:

- `localStorage` tokens are exposed to XSS.
- No refresh token flow.
- No token revocation.
- `AuthProvider` does not verify token on startup.
- JWT secret usage is inconsistent. Fallback constants exist, but some calls use `process.env.JWT_SECRET` directly.

### Validation

Implemented:

- Frontend validation in login and signup forms.
- Mongoose required fields for core user, appointment, medical record, and symptom fields.
- Flask LLM endpoint checks for missing `symptoms` field.

Missing or weak:

- No centralized backend validation library such as Zod, Joi, or express-validator.
- No input sanitization.
- No strict schema validation for LLM output.
- No date validation for appointment creation.
- No ObjectId validation before database operations.
- Role-specific Mongoose requirements are incorrectly configured.

### Security Risks

| Risk | Location | Impact | Recommendation |
|---|---|---|---|
| Inconsistent JWT secret usage | `backend/auth.js`, `backend/middleware.js` | Login/protected routes can fail or use different secrets | Use a single config helper and fail fast if `JWT_SECRET` is missing in production |
| Hardcoded fallback JWT secret | `backend/auth.js`, `backend/middleware.js` | Predictable tokens in environments without configured secret | Use `.env.example` and reject production boot without secret |
| Token in `localStorage` | `frontend/src/services/api.js` | XSS can steal bearer token | Consider HttpOnly secure cookies or strong XSS hardening |
| Unrestricted CORS | `backend/index.js` | Any origin can call API in browsers | Configure allowed origins |
| Missing rate limiting | Auth routes | Brute-force login risk | Add rate limiter on auth endpoints |
| Thin backend authorization | `backend/routes.js` | Users can create records/appointments with arbitrary IDs | Enforce role and ownership checks |
| Sensitive request logging | `backend/auth.js` logs registerPatient body | Password or PHI may appear in logs | Remove request-body logs |
| External AI data sharing | `backend/routes.js`, `backend/llm-service/llm.py` | Patient symptom text leaves local system | Add consent, redaction, audit, and provider policy review |
| No production headers | `backend/index.js` | Missing common web hardening | Add Helmet and secure deployment headers |
| No HTTPS enforcement | Deployment not implemented | Tokens and PHI vulnerable in transit outside local dev | Deploy only behind HTTPS |

### `frontend/src/contexts`

This folder isolates authentication context logic.

- `auth-context.js` defines the context object.
- `AuthContext.jsx` defines the provider and auth actions.
- `useAuth.js` defines a safe hook for consuming the context.

This separation improves Fast Refresh behavior and avoids exporting non-component values from the provider file.

### `frontend/src/services`

This folder contains the frontend API abstraction.

- `api.js` centralizes the base URL, token persistence, request helper, auth calls, and domain API methods.

This gives components a simple interface and keeps token headers in one place.

### `frontend/src/assets`

This folder contains the default `react.svg` asset from the Vite template. It is not currently imported by the application.

## 12. Bugs / Technical Debt

### Code Smells

- `backend/routes.js` and `backend/auth.js` contain inline controller/business logic instead of separated controllers and services.
- `DoctorDashboard.jsx` uses extensive inline CSS, unlike other components that use CSS files.
- `DoctorDashboard.jsx` imports unused icons such as `Search`, `Filter`, `Download`, `Play`, and `Pause`.
- `currentConsultation` exists in `DoctorDashboard.jsx` but is not meaningfully used.
- `SymptomLog` and `SymptomLogDoctor` duplicate symptom concepts; only `SymptomLogDoctor` is used.
- `register` and `registerPatient` duplicate registration logic.
- `frontend/src/App.css` is leftover starter CSS and mostly commented out.
- `frontend/package.json` includes `axios`, but the frontend service uses `fetch`.
- `backend/package.json` includes `multer`, but no file upload route exists.
- `backend/llm-service/__pycache__` is present/tracked and should be ignored.

### Functional Bugs and Risks

- JWT fallback constant is defined but not consistently used in login and middleware verification.
- Role-specific schema requirements are incorrectly configured in `models.js`.
- Doctor mock consultation uses hardcoded `patientId: '507f1f77bcf86cd799439011'`, which may not exist.
- Appointments tab appears in the doctor dashboard but no appointment content panel is implemented.
- Patient dashboard disabled buttons look like future features but have no behavior.
- "Generate SOAP Notes" button appears after mock transcription but does not run generation logic.
- "Generate timeline", "Ask Clinsight AI", "Share", and "Select Doctor" are not wired.
- Patient dashboard has no visible logout flow.
- Frontend hardcodes `http://localhost:3000/api`, limiting non-local deployment.

### Performance Concerns

- No pagination for appointments, records, or symptoms.
- Symptom submission refetches all symptoms after every create.
- No indexes on common query fields such as `userId`, `doctorId`, `patientId`, and `createdAt`.
- LLM call is synchronous inside the symptom POST request.
- No timeout around the Node-to-Flask Axios call.
- No caching for doctors list or records.

### Security Issues

- JWT token stored in `localStorage`.
- Backend CORS allows all origins.
- No rate limiting on auth endpoints.
- No backend request validation library.
- No ObjectId validation.
- No role enforcement on sensitive create endpoints.
- Request body logging in `registerPatient` can expose secrets or PHI.
- External AI provider receives symptom text without implemented consent or redaction controls.
- README claims privacy/HIPAA concepts that are not fully implemented in code.

### Scalability Limitations

- AI service is a local Flask process with no queue, worker pool, or retry policy.
- Express and Flask services communicate through hardcoded local URL.
- No deployment configuration for multi-service orchestration.
- No background job processing for AI tasks.
- No observability, tracing, metrics, or structured logs.
- No multi-tenant organization/hospital model.
